# Task D3 — LogiEdge mapped to the 10-stage Edge ML pipeline (Module 4)

Source text for Final Report Section 3. Each stage gives what happens **in LogiEdge**, plus the
file that shows it. All figures refer to the committed models (M1 `986ebc19…`, M2 `c331664a…`,
M3 `f220ec06…`), dataset `d2ec8995…` and statistics `20f01b2d…`.

| # | Stage | What happens in LogiEdge | Evidence |
|---|---|---|---|
| 1 | Problem definition and constraints | FreightBridge needs every refrigerated truck to classify cargo state as Normal / Warning / Critical and raise a cab alert within a 90 s SLA, also during cellular dead zones. The edge node therefore runs inference locally, keeps a durable alert log, and syncs to the operations centre when the link returns. | `scenario_architecture/constraint_analysis.md`, `system_architecture.png` |
| 2 | Data acquisition | `simulator.py` publishes per-truck MQTT streams to Mosquitto: temperature at 1 Hz (QoS 1), compressor vibration RMS at 0.5 Hz (QoS 0) and door events (QoS 2), plus a truth topic. Eight real-time recordings (one Normal, two temperature-drift Warning, five Critical: vibration, temperature and combined faults) form the training data, each with a SHA-256 in `dataset_provenance.json`. | `data_pipeline/simulator.py`, `training/provenance/` |
| 3 | Data preprocessing and labelling | Raw readings are smoothed with an MA-5 filter, cut into 30 s windows every 10 s, and labelled from the truth stream (Critical above a 3 °C offset or with failure vibration, Warning at 1–3 °C), excluding windows that span a class change. Each recording is split in time order with 3 windows purged between train and validation, so no window shares history across the split (309 train / 86 validation). | `data_pipeline/preprocessing.py`, `training/labeling.py`, `training/split_report.json` |
| 4 | Feature engineering and fusion | Each window becomes six features (`temp_mean`, `temp_std`, `temp_rate_C_per_min`, `vib_rms`, `vib_peak`, `vib_kurtosis`), fused at feature level into one vector and z-scored with the training statistics frozen in `training_stats.npy`. Those statistics are baked into the container unchanged, because shifting them by +3σ drops M2's accuracy from 100 % to 91.9 % and its Critical recall to 84.1 %. | `data_pipeline/mqtt_architecture.md`, `data_pipeline/results/normalisation_experiment.json` |
| 5 | Model selection and training | A 6→32→16→3 dense classifier (803 parameters) is trained for 150 fixed epochs with Adam, class weights and seed 42, with no model selection on validation data. It was chosen because a few KiB of weights runs on the Raspberry Pi 5 CPU without an accelerator. | `training/train_model.py`, `training/models/m1_metrics.json` |
| 6 | Model evaluation | Every converted `.tflite` reaches 100 % on the 86 validation windows, but on the fresh fault stream the 30 s window lags class changes, so Critical recall is 86 % for M1 and M2 and 82 % for M3 (4/4 fault episodes caught within 90 s, 0/80 false alarms). This gap is why F3 recommends shadow mode before any variant controls alerts on its own. | `optimisation/results/validation_tflite.json`, `optimisation/deployment_recommendation.md` |
| 7 | Model optimisation | M2 is full-INT8 post-training quantisation calibrated on 256 distinct training windows, and M3 adds 35 % structured neuron pruning before INT8 (400 parameters, 3.67 KiB, against 4.51 KiB for M2 and 5.20 KiB for M1). All three are far inside the latency budget, so M2 is chosen for its smaller OTA size with no recall loss compared with M1. | `training/convert_ptq.py`, `training/prune_quantise.py`, `optimisation/results/pareto_chart.png` |
| 8 | Conversion and packaging | The model is converted to a TFLite flatbuffer with int8 input and output and packaged in a `python:3.11-slim` image running `ai-edge-litert` 2.3.0, which gives bit-identical predictions to TensorFlow on all 86 validation windows. `model.tflite` is the last Dockerfile layer, so a model swap rebuilds only 1 of 10 layers. | `inference/Dockerfile`, `inference/results/runtime_*.json`, `inference/results/ota_layer_cache.json` |
| 9 | Deployment and OTA update | A seven-task Ansible playbook copies the model and `reference_dist.json` to `/opt/logibridge`, stops the container only if one of those files changed, pulls the image from the local registry, and lets `docker_container` start or recreate the container only when its image, environment or mounts differ; a second unchanged run reports `changed=0`. A model update ships the 9.7 KB layer instead of the 95.30 MB image, 0.83 MB instead of 8,100.65 MB for 85 trucks (99.99 % saving). | `deployment/logibridge_deploy.yml`, `deployment/results/`, `deployment/ota_strategy.md` |
| 10 | Monitoring and maintenance | Every inference, alert, door event and drift value goes into a hash-chained SQLite log, replayed alerts-first over QoS 1 after a dead zone (33/33 entries delivered, no duplicates). A PSI monitor on P(Normal) over the last 100 inferences alerted 120 s after a combined fault began (peak 2.41) and returned to 0.000 about 17 minutes after it ended, and a drift alert without matching classifier alerts flags a sensor problem for the next recording and retraining cycle. | `inference/results/e2e_offline_sync.json`, `monitoring/results/drift_run_summary.json` |
